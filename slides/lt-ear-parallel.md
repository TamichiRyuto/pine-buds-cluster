## 2. 並列計算のおさらい — MPI と OpenMP

**図解: 並列化には 2 つのレベルがある**

```
┌─────────── ノード A (メモリ空間 A) ───────────┐   ┌─────────── ノード B (メモリ空間 B) ───────────┐
│  ┌────────┐  ┌────────┐                      │   │  ┌────────┐  ┌────────┐                      │
│  │ コア 0 │  │ コア 1 │  ← スレッドレベル並列 │   │  │ コア 0 │  │ コア 1 │                      │
│  └────────┘  └────────┘     = OpenMP          │   │  └────────┘  └────────┘                      │
│        ＼        ／                           │   │        ＼        ／                           │
│      同じ配列を共有 (共有メモリ)              │   │      同じ配列を共有                           │
└───────────────────────────────────────────────┘   └───────────────────────────────────────────────┘
                    ↑                                                   ↑
                    └──────── クラスタレベル並列 = MPI ─────────────────┘
                       メモリが物理的に別。明示的にメッセージを送り合う
                       MPI_Send / MPI_Recv / MPI_Barrier / MPI_Allreduce
```

| | OpenMP | MPI |
|---|---|---|
| 単位 | スレッド | プロセス (ランク) |
| メモリ | 共有 | 分散 (別空間) |
| 書き方 | `#pragma omp parallel for` | `MPI_Send` / `MPI_Recv` |
| コスト | 安い (ns〜μs) | 高い (μs〜ms、ネットワーク次第) |
| 今回の担当 | イヤホン**内**の 2 コア (**未達**) | イヤホン**間** (左 ⇄ 右) |

**GEMM (行列積) を 2 ランクに分けると**

```
C = A · B      A の行を [m0, m1) で分割
rank 0 → 行 0..15 を計算    rank 1 → 行 16..31 を計算
                ↓ MPI_Send / MPI_Recv で結果を集約 ↓
             rank 0 が全体の checksum を検証して PASS/FAIL
```

> Note: HPC の定石「ノード間は MPI、ノード内は OpenMP」のハイブリッド構成。
> 今回はこの標準的な書き方をそのまま持ち込むのがテーマ。OpenMP 側は API だけ揃えた段階。

## 3. 今回のクラスタ構成

```
        ┌───────────────────────┐   Bluetooth (IBRT / BESAUD)   ┌───────────────────────┐
        │  右バッズ  rank 0     │◀────── L2CAP 上の TWS ───────▶│  左バッズ  rank 1     │
        │  BES2300YP            │        制御チャネル            │  BES2300YP            │
        │  Cortex-M4F ×2        │   cmdcode 0x8201 (自作)        │  Cortex-M4F ×2        │
        └───────────────────────┘                                └───────────────────────┘
                    │                                                        │
                    └────────── Bluetooth SPP (自作ログチャネル) ────────────┘
                                              ▼
                                    Windows PC (COM6)
                                  #23 GEMM-MPI ... PASS
```

- **ノード間 = MPI**: 自作 MPI サブセットを IBRT (イヤホン同士の TWS リンク) に載せた
- **ノード内 = OpenMP**: Stage-1 は逐次スタブ (API だけ本物と同じ)。2 コア目は今回未使用 ← **正直に言う**
- **観測 = SPP**: Bluetooth 上のシリアルポート。UART とは独立の経路

> Note: rank は左右ストラップ由来で固定だが、**IBRT のロール (master/slave) は起動ごとに入れ替わる**。
> スライドの MASTER/SLAVE 表記は nv_role (不揮発の初期値)。この違いが §11 の「slave のログが
> 電波に乗らない」問題に効いてくる。

## 5. なぜ「普通のワイヤレスイヤホン」ではダメだったのか

**当初の構想**: 手持ちの TWS (左右が独立した完全ワイヤレス) でやりたかった。
→ **自作コードを載せる手段が見つからなかった。**

```
自作コードをイヤホンで動かすのに必要なもの     手元で調べた範囲の市販 TWS   PineBuds Pro
──────────────────────────────────────────────────────────────────────────────────────
① ファームウェアのソース / SDK                 非公開                  OSS (OpenPineBuds)
② 書き込み経路 (署名されていない FW を焼ける)  書き込み手段が非公開    bestool で普通に焼ける
③ 標準出力 = デバッグ UART が外に出ている       出ていない              充電ケースが UART を兼ねる
④ 左右間リンクを叩ける API                     非公開の独自 TWS        IBRT の API がヘッダで見える
⑤ 文鎮化した時の復旧手段                       見つからなかった        工場 FW + 純正ライタが配布
```

- ① 〜 ③ のどれか 1 つでも欠けると **「コードを書いても載せられない」** ので実験自体が成立しない
- 一般的な TWS は音質・ANC・電池のために作られていて、**ユーザーが計算を載せる想定がそもそも無い**
- 分解して SWD を引き出す道もあるが、**左右 2 個を同じ状態に保って何十回も焼き直す**用途には向かない
- **これは手元の機種と自分が調べられた範囲の話**で、すべての TWS がそうだと主張するものではない

**→ 「オープンソースファーム + ケースが UART プログラマ」を両立している TWS が、探した範囲で
ここだけだったので購入。**

> Note: 「Linux が動くイヤホン」ではなく「自分のコードを載せられるイヤホン」を探した、という話にする。
> 文鎮化リスクの話は共感を得やすい。実際いちばん最初にやったのは工場ファームの全量バックアップ。
> ⑤ の PineBuds 側の根拠は pine64 公式ページ (Windows programmer utility v1.48 + `AC08_20221102.bin`)。

## 7. 実装の山場 ① — SDK にソースが無い

**問題**: 左右リンクの本体 `services/ibrt_core/` は **`inc/` と `lib/` しか無い**。
`src/` が存在しない = **プリビルトの `.a` しか無い**。

**やったこと**: `libtws_ibrt_enhanced_stack_anc_RTX.a` を**逆アセンブルして仕様を確定した。**

| 調べたこと | ヘッダの記述 | 逆アセンブルした実体 | 影響 |
|---|---|---|---|
| 送信ペイロード上限 | `APP_TWS_CTRL_BUFFER_MAX_LEN` = **300** | 実行時 assert は **672** | 300 と 672 のどちらで切るか設計が変わる |
| RX ハンドラのスレッド | 記述なし | **`BesbtThread`** (BT スタック本体のループ) | **ここをブロックすると BT が全部止まる** |
| 送信ポンプ | 記述なし | 同じループの 1 行上 | 計算スレッドを別に立てる必要がある |

**結論した設計**

- 計算は **専用スレッド**に隔離 (`app_init` 末尾で同期実行すると電源管理まで止まる)
- ペイロードは **実測で決める**。起動時に 4 → 64 → … → 668 B を掃引するモード (`[mpi-t1]`) を実装
  - **実測: `max_payload=512`** (668 は TIMEOUT)。ヘッダの 300 でも blob の 672 でもなかった
- **256 B を超えるメッセージは 268 B フレーム (ペイロード 256 B) に断片化**。
  クレジット制御 W=2 で in-flight を 536 B に抑える
- 追加 RAM は **MPI トランスポート 5.5 KB + SPP ログ 9.3 KB ≒ 15 KB** — RAM 残 330 KB に対して余裕

> Note: 「ヘッダを信じるな、リンクされるバイナリを信じろ」。ここは技術者ウケが良いはず。
> 300 / 672 / 512 の 3 つの数字を並べるのがこのスライドの山。

## 8. 実装の山場 ② — 実機は 1 発では動かない

**焼いて動かすまでに踏んだ地雷 (全部ログが残っている)**

| # | 症状 | 原因 | 対処 |
|---|---|---|---|
| 1 | `finalize done` の 2 秒後に **MemFault で無限リブート** (17.5 秒周期) | RTX でスレッドが自分自身を終了させるとスケジューラが壊れる | スレッドを return させず **park** |
| 2 | ケースに入れて充電起動すると **BT スタックが上がらない** (`size=1` に縮退) | `CHARGER_PLUGINOUT_RESET=1` の副作用 | `target.mk` を **0** にパッチ |
| 3 | 走行中に **リンクが切れる** | 充電器の PLUGIN イベントが `CLOSE_BOX` を注入していた | 箱イベントを遮断 |
| 4 | 起動 15〜60 秒で **勝手に電源が落ちる** | `FULL_CHARGING` → `app_shutdown()` (満充電シャットダウン) | `app_shutdown()` を `if (0)` 化 |
| 5 | PC と **再ペアリングできない** | 通常ビルドは page scan だけで inquiry scan を出さない | 専用ビルドで discoverable |
| 6 | SPP ログの **先頭 512 B だけ二重に届く** | SDK が 1 回の RFCOMM open で `CONNECTED` を **2 回**上げる | 送信 FSM で重複を無視 |

**クラッシュログ (Run 2, 両バッズ・毎ブート再現)**

```
[mpi] finalize done rank=0
### EXCEPTION ###
CFSR =00000082   ; MMARVALID | DACCVIOL
MMFAR=00000034
FaultCause: (Data access violation)
Current Task    : 0     <- os_tsk.run == NULL = 走るタスクが居ない
New Running Task: 255   ; idle TCB
```

**`MMFAR = 0x34` が犯人を名指しした**: 0x34 は RTX の `OS_TCB` 構造体の `swap_out_time`
オフセットと**厳密に一致**する。`__RTX_CPU_STATISTICS__` が有効なため、スレッドが自己終了すると
`os_tsk.run` が NULL になった直後に `os_tsk.run->swap_out_time` を書きに行っていた。

**効いた運用**: 純ロジックは全部ホストのテストを先に書いた。実機で出た SPP のバグも
5 本のテスト (F9〜F13) に落としてから直した。
(#2〜#5 は SDK 側のパッチなのでホストテストの対象外)

> Note: 逆アセンブルではなく `nm` でシンボル解決して犯人を特定した、という小ネタも入る。
> 「組み込みは電源とペアリングで死ぬ」は共感ポイント。

## 9. 実装の山場 ③ — 観測をワイヤレスにする / 耳で操作する

**やりたかったこと**: USB ケーブルで繋がったイヤホンは「イヤホン」ではない。

**① Bluetooth SPP に自作ログチャネルを生やした**

- `COMPUTE_TRACE` のログ行をリングバッファに積み、**SPP (= Bluetooth 上のシリアルポート) で
  Windows に流す**
- PC 側は `spp_tail.py COM6` で受けるだけ。`#<seq>` 番号で**欠落・重複を機械検出**
- **UART とは独立の経路**なので、原理的に USB は要らない
  (※ 実測はすべて USB 接続下。「USB を抜いて動かした」ランはまだ取っていない)

**② 5 連タップで GEMM を再実行できるようにした**

- タッチパッドは BES2300YP の**電源キー入力**。ジェスチャは SDK がソフトで判定 (`hal_key.c`)
- 単タップ〜4 連・長押しは既存機能で埋まっていた → **未割当の `RAMPAGECLICK` (5 連)** を奪う
- 調停ロジックは**ホストで 8 テスト書いてから**実装した

```
 ① 5 連タップ          → ② 相手に START を送る    → ③ 相手も起きる      → ④ 両バッズで GEMM
   叩かれた側だけが         左右間の制御チャネルに       受信側は待機セマフォ     rank 0 が checksum 検証
   キーイベントを受け取る    5 バイトのフレームを 1 本    を解放して計算に入る     [mpi] run #1 done rank=0
```

実行中の連打は捨てる。相手の START が落ちたらタップした側だけが走り、
5 秒のストール検出を経て縮退で完走する。

> Note: デモ的に一番「おっ」となるところ。ケースの中でもタッチは反応する。

| 起動時 | 自動 | PASS, size=2 | 12 ms |
| #1 | **右**を 5 連タップ | PASS, size=2 | 128 ms |
| #2 | **左**を 5 連タップ | PASS, size=2 | **5 ms** |
| #3 | **右**を 5 連タップ | PASS, size=2 | 115 ms |
| #4 | **左**を 5 連タップ | PASS, size=2 | 83 ms |

- タップした側が先に走り出し、相手は START の伝搬待ちで合流するので **タップした側 (rank 0) の
  elapsed が伸びる** (#1 / #3)
- **正直な注記**: このランで COM6 に出たのは**左 (rank 1) のログだけ**。IBRT の slave 側の SPP 送信は
  スタック上は成功扱いなのに電波に乗らないため、rank 0 の `GEMM-MPI` 行は UART 側にしか
  出ていない (**未解決**)

> Note: 「耳を 5 回叩くと両バッズで行列積が走り、実行ログが Bluetooth で PC に流れてくる」で締める。
> 「PASS 行そのものが飛んだ」とは言わない — 飛んだのは実行ログ (`run #n trigger/done`)。

## 12. 結果 ③ — 数字で見る

| 指標 | 実測値 | コメント |
|---|---|---|
| GEMM N=32 単コア (1 ノード) | **5 〜 10 ms** | Phase 0.5 のゴールデン基準 |
| GEMM N=32 2 ノード MPI | **12 〜 13 ms** | 通信込み。**並列化して遅くなった** |
| 左右間 実効ペイロード | 512 B | ヘッダの 300 でも blob の 672 でもない |
| アイドルからの往復 RTT | 最大 407 ms | ランごとに変動 (avg 93 〜 278 ms) |

```
    単コア 5〜10 ms   →   2 ノード 12〜13 ms
         分散したぶんだけ遅くなった
```

**12〜13 ms の読み方**

- 分割で浮く計算は数 ms (単コア 5〜10 ms の半分)。リンクが張れている間の往復も数 ms。
  差し引きで通信のほうが勝つ = **N=32 では分散する意味がない**
- **407 ms の RTT は `[mpi-t1]` の 100 回連続プローブ中の値**であって、GEMM 実行中の
  レイテンシではない。省電力 (sniff) に落ちた状態から叩き起こすとここまで伸びる
  (タップ再実行の 128 ms がこれ)

**なぜ遅いのか = この実験の本題**

| | |
|---|---|
| ① 分割で浮く計算 | 2 × 32³ ≒ 65,000 flop を半分に → 数 ms |
| ② 往復に要る時間 | リンクが生きていれば数 ms → ① とほぼ相殺、むしろ負け |
| ③ アイドルからの往復 | 最大 407 ms = 単コア GEMM 40 〜 80 回ぶん |

**→「計算量 / 通信量」が小さい問題を分散してはいけない。**
速くはならなかった。が、HPC の教科書どおりの結論を、耳の中で定量的に再現できた。

> Note: 「速くなりませんでした」で終わらせず、**なぜ遅いかが定量的に説明できる**ことを成果として出す。
> 「通信 1 回で計算 100 回ぶん」のような盛った倍率は使わない (実測レンジは 40〜80 倍)。

## 13. わかったこと / できていないこと

**わかったこと**

- **標準 API のまま実機に載る**: `bench/gemm_mpi_omp.cpp` は本物の OpenMPI でも自作アダプタでも
  無改変でビルドでき、3 経路すべて checksum 一致。**アダプタ境界の設計が正しかった**
- **ソースが無くても仕様は確定できる**: プリビルト `.a` の逆アセンブルで、ヘッダと食い違う
  実挙動 (上限 672、RX が BT スタックスレッド) を根拠付きで確定できた
- **組み込みの敵は計算ではない**: 6 個の地雷のうち計算に起因するものはゼロ。
  全部が電源・接続・RTOS・SDK の仕様
- **ホストで TDD できる形に切ると実機デバッグが激減する**: 実機で 1 回試す前にホストで
  1,788 checks。実機で出た SPP のバグもホストのテストに落としてから直した

**できていないこと (正直に)**

- **ノード内 2 コア並列は未達**: OpenMP は Stage-1 の逐次スタブのまま。2 個目のコア (CP) は
  音声処理が使っており、計算に取ると取り合いになる
- **slave 側のログが電波に乗らない**: IBRT の snoop リンクでは slave の SPP 送信が
  スタック上は成功扱いなのに実際には飛ばない。rank 0 が master の時しか PC に届かない
- **音楽再生との同時実行は未検証**: 「イヤホンとして使いながら裏で計算」はまだ道半ば
- **N を大きくした時のスケーリングは未計測**: RAM 330 KB の上限は N≈128。
  そこまでで通信コストを償却できるかは未検証

    └────────────────────────────────────────────────────────────┘

  ✅ 標準 MPI API で書いたベンチが、無改変で耳の中で PASS した (OpenMP は互換スタブ)
  ✅ checksum=32768.000000 厳密一致 / 両バッズ size=2 / EXCEPTION 0 回

## 付録: 想定質問

1. **「N を大きくすれば通信を償却できるのでは？」**
   RAM 空き 330 KB で float32 の行列 3 枚を置くと N=128 が上限。そこまでで逆転するかは未計測。
2. **「OpenMP はスタブですよね？」**
   PASS したのは API 互換性 (無改変ビルド + 3 経路 checksum 一致)。並列実行は Stage-2。
3. **「RTT が sniff のせいなら sniff を切れば？」**
   sniff 制御はプリビルト `.a` の中で、公開ヘッダに叩ける API が無い。改善候補の筆頭。
4. **「checksum=32768 は全要素 1 でしょ。チートでも通るのでは？」**
   実機判定は精度非依存の決定的ケースとして意図的に選んだもの。機能検証はホストの 1,788 checks と
   本物の OpenMPI とのゴールデンリファレンス照合が担っている。
5. **「ESP32 を 2 個並べれば 10 分では？」**
   性能が目的なら PC 1 台でいい。狙いは「市販品として耳に入る完成品を、分解せず無改造のまま
   クラスタにできるか」。ペアリング済みの左右リンクにユーザーコードから相乗りしたのが技術的な点。
