## 2. 並列計算のおさらい — MPI と OpenMP

**図解: 並列化には 2 つのレベルがある**

```
┌─────────── ノード A (メモリ空間 A) ───────────┐   ┌─────────── ノード B (メモリ空間 B) ───────────┐
│  ┌────────┐  ┌────────┐                      │   │  ┌────────┐  ┌────────┐                      │
│  │ コア 0 │  │ コア 1 │  ← スレッドレベル並列 │   │  │ コア 0 │  │ コア 1 │                      │
│  └────────┘  └────────┘     = OpenMP          │   │  └────────┘  └────────┘                      │
│        ＼        ／                           │   │        ＼        ／                           │
│      同じ配列を共有 (共有メモリ)              │   │      同じ配列を共有                           │
└───────────────────────────────────────────────┘   └───────────────────────────────────────────────┘
                    ↑                                                   ↑
                    └──────── クラスタレベル並列 = MPI ─────────────────┘
                       メモリが物理的に別。明示的にメッセージを送り合う
                       MPI_Send / MPI_Recv / MPI_Barrier / MPI_Allreduce
```

| | OpenMP | MPI |
|---|---|---|
| 単位 | スレッド | プロセス (ランク) |
| メモリ | 共有 | 分散 (別空間) |
| 書き方 | `#pragma omp parallel for` | `MPI_Send` / `MPI_Recv` |
| コスト | 安い (ns〜μs) | 高い (μs〜ms、ネットワーク次第) |
| 今回の担当 | イヤホン**内**の 2 コア | イヤホン**間** (左 ⇄ 右) |

**GEMM (行列積) を 2 ランクに分けると**

```
C = A · B      A の行を [m0, m1) で分割
rank 0 → 行 0..15 を計算    rank 1 → 行 16..31 を計算
                ↓ MPI_Send / MPI_Recv で結果を集約 ↓
             rank 0 が全体の checksum を検証して PASS/FAIL
```

> Note: HPC の定石「ノード間は MPI、ノード内は OpenMP」のハイブリッド構成。
> 今回はこの標準的な書き方をそのまま持ち込むのがテーマ。

        ┌───────────────────────┐   Bluetooth (IBRT / BESAUD)   ┌───────────────────────┐
        │  右バッズ  rank 0     │◀────── L2CAP 上の TWS ───────▶│  左バッズ  rank 1     │
        │  BES2300YP            │        制御チャネル            │  BES2300YP            │
        │  Cortex-M4F ×2        │   cmdcode 0x8201 (自作)        │  Cortex-M4F ×2        │
        │  SRAM 992KB           │   実効ペイロード 512 B         │  SRAM 992KB           │
        └───────────────────────┘                                └───────────────────────┘
                    │                                                        │
                    └────────── Bluetooth SPP (自作ログチャネル) ────────────┘

                                    Windows PC (COM6)

## 5. なぜ「普通のワイヤレスイヤホン」ではダメだったのか

**当初の構想**: 手持ちの一般的な TWS イヤホンでやりたかった。→ **手段がゼロだった。**

```
自作コードをイヤホンで動かすのに必要なもの        一般的な TWS      PineBuds Pro
──────────────────────────────────────────────────────────────────────────────
① ファームウェアのソース / SDK                    非公開            OSS (OpenPineBuds)
② 書き込み経路 (署名されていないFWを焼ける)       署名検証で拒否    bestool で普通に焼ける
③ 標準出力 = デバッグ UART が外に出ている          出ていない        充電ケースが UART を兼ねる
④ 左右間リンクを叩ける API                        非公開の独自TWS   IBRT の API がヘッダで見える
⑤ 文鎮化した時の復旧手段                          無い (=終わり)    工場ファーム + 純正ライタが配布
```

- ① 〜 ③ のどれか 1 つでも欠けると **「コードを書いても載せられない」** ので実験自体が成立しない
- 一般的な TWS は音質・ANC・電池のために作られていて、**ユーザーが計算を載せる想定がそもそも無い**
- 分解して SWD を引き出す道もあるが、**左右 2 個を同じ状態に保って何十回も焼き直す**用途には向かない

**→ 「オープンソースファーム + ケースが UART プログラマ」を両立している TWS が実質ここだけだったので購入。**

> Note: 「Linux が動くイヤホン」ではなく「自分のコードを載せられるイヤホン」を探した、という話にする。
> 文鎮化リスクの話は共感を得やすい。実際いちばん最初にやったのは工場ファームの全量バックアップ。

## 7. 実装の山場 ① — SDK にソースが無い

**問題**: 左右リンクの本体 `services/ibrt_core/` は **`inc/` と `lib/` しか無い**。
`src/` が存在しない = **プリビルトの `.a` しか無い**。

**やったこと**: `libtws_ibrt_enhanced_stack_anc_RTX.a` を**逆アセンブルして仕様を確定した。**

| 調べたこと | ヘッダの記述 | 逆アセンブルした実体 | 影響 |
|---|---|---|---|
| 送信ペイロード上限 | `APP_TWS_CTRL_BUFFER_MAX_LEN` = **300** | 実行時 assert は **672** | 300 と 672 のどちらで切るか設計が変わる |
| RX ハンドラのスレッド | 記述なし | **`BesbtThread`** (BT スタック本体のループ) | **ここをブロックすると BT が全部止まる** |
| 送信ポンプ | 記述なし | 同じループの 1 行上 | 計算スレッドを別に立てる必要がある |

**結論した設計**

- 計算は **専用スレッド**に隔離 (`app_init` 末尾で同期実行すると電源管理まで止まる)
- ペイロードは **実測で決める**。起動時に 4 → 64 → … → 668 B を掃引して上限を測るモード (`[mpi-t1]`) を実装
  - **実測: `max_payload=512`** (668 は TIMEOUT)。ヘッダの 300 でも blob の 672 でもなかった
- 512 B を超えるメッセージは **断片化 + クレジット制御 (W=2)**。in-flight を 536 B に抑える
- 追加メモリは **約 5.5 KB** (合計 22.7 KB) — RAM 残 330 KB に対して余裕

> Note: 「ヘッダを信じるな、リンクされるバイナリを信じろ」。ここは技術者ウケが良いはず。

## 8. 実装の山場 ② — 実機は 1 発では動かない

**焼いて動かすまでに踏んだ地雷 (全部ログが残っている)**

| # | 症状 | 原因 | 対処 |
|---|---|---|---|
| 1 | `finalize done` の 2 秒後に **MemFault で無限リブート** (17.5 秒周期) | RTX で計算スレッドが自分自身を終了させるとスケジューラが壊れる | スレッドを return させず **park** する |
| 2 | ケースに入れて充電起動すると **BT スタックが上がらない** (`size=1` に縮退) | `CHARGER_PLUGINOUT_RESET=1` の副作用 | `target.mk` を **0** にパッチ |
| 3 | 走行中に **リンクが切れる** | 充電器の PLUGIN イベントが `CLOSE_BOX` を注入していた | 箱イベントを遮断 |
| 4 | 起動 15〜60 秒で **勝手に電源が落ちる** | `FULL_CHARGING` → `app_shutdown()` (満充電シャットダウン) | `app_shutdown()` を `if (0)` 化 |
| 5 | PC と **再ペアリングできない** | 通常ビルドは page scan しか出さず inquiry scan を出さない | `SPP_LOG_PAIRING=1` ビルドで discoverable にする |
| 6 | SPP ログの **先頭 512 B だけ二重に届く** | SDK が 1 回の RFCOMM open で `CONNECTED` を **2 回**上げる | 送信 FSM で重複 CONNECTED を無視 + 5 s タイムアウト再送 |

**クラッシュログ (Run 2, 両バッズ・毎ブート再現)**

```

### EXCEPTION ###
PC =002AC1BE, ExceptionNumber=-12
XPSR=2100000B          ; IPSR=0x0B = SVCall 実行中
CFSR =00000082         ; MMARVALID | DACCVIOL
FaultInfo : (MemFault)  FaultCause: (Data access violation)
Current Task    : 0
New Running Task: 255   ← 次に走るタスクが居ない
```

> Note: 逆アセンブルではなく `nm` でシンボル解決して犯人を特定した、という小ネタも入れられる。

## 9. 実装の山場 ③ — 観測をワイヤレスにする / 耳で操作する

**やりたかったこと**: USB ケーブルで繋がったイヤホンは「イヤホン」ではない。

**① Bluetooth SPP に自作ログチャネルを生やした**

- `COMPUTE_TRACE` のログ行をリングバッファに積み、**SPP (RFCOMM) で Windows に流す**
- PC 側は `spp_tail.py COM6` で `#<seq>` 付きの行を受けるだけ。**欠落・重複を seq で機械検出**
- 結果: **USB を抜いても `GEMM-MPI ... PASS` が PC に届く**

**② 5 連タップで GEMM を再実行できるようにした**

- タッチパッドは BES2300YP の**電源キー入力**。ジェスチャは SDK がソフトで判定 (`hal_key.c`)
- 単タップ〜4 連・長押しは既存機能で埋まっていた → **未割当の `RAMPAGECLICK` (5 連)** を奪う
- タップした側が相手に **START フレーム (cmdcode 0x8201 / kind 5)** を送って両方で走らせる
- 実行中の連打は捨てる。この調停ロジックは**ホストで 8 テスト書いてから**実装した

```
 [ 5 連タップ ]
   ↓ app_key_compute_run event 12
 タップした側: [mpi] run #1 trigger=local peer_notified=1  ──START(0x8201)──▶ 相手
 相手側      : [mpi] run #1 trigger=peer
   ↓ 両方で GEMM-MPI 実行 → rank 0 が checksum を検証
 [mpi] run #1 done rank=0
```

> Note: デモ的に一番「おっ」となるところ。ケースの中でもタッチは反応する。

## 12. 結果 ③ — 数字で見る

| 指標 | 実測値 | コメント |
|---|---|---|
| GEMM N=32 単コア (1 ノード) | **5〜9 ms** | Phase 0.5 のゴールデン基準 |
| GEMM N=32 2 ノード MPI | **12〜13 ms** | **並列化して遅くなっている** ← 正直に言う |
| 左右間 RTT (100 回) | min 44 / avg 169 / max **407 ms** | Bluetooth の sniff 復帰待ちで大きく揺れる |
| 左右間 実効ペイロード | **512 B** | ヘッダの 300 でも blob の 672 でもなかった |
| 追加 RAM | **5.5 KB** (合計 22.7 KB) | RAM 残 330 KB に対して余裕 |
| ホストテスト | **1,788 checks** / 8 バイナリ | 実機に焼く前に全部緑にする運用 |
| コード規模 | アダプタ 926 行 / ファーム統合 1,656 行 / テスト 1,846 行 | **テストが本体より多い** |
| 設計ドキュメント | 2,601 行 | SDK の逆アセンブル結果の記録が大半 |

**なぜ遅いのか (= この実験の本当の面白さ)**

```
N=32 の GEMM の計算量      = 2 × 32³ ≒ 65,000 flop  →  M4F @104MHz で数 ms
左右間 1 往復のレイテンシ  = 44 〜 407 ms
                             ~~~~~~~~~~~~~~~~~~
    通信 1 回で、計算 100 回ぶんの時間が飛ぶ。
    → 「計算量 / 通信量」が小さい問題を分散してはいけない、という HPC の教科書どおりの結論を
       耳の中で再現した。N を大きくすれば逆転するが、今度は RAM (330 KB) が先に尽きる。
```

> Note: 「速くなりませんでした」で終わらせず、**なぜ遅いかが定量的に説明できる**ことを成果として出す。

---

## 13. わかったこと / できていないこと

**わかったこと**

- **標準 API のまま実機に載る**: `bench/gemm_mpi_omp.cpp` は本物の OpenMPI でも自作アダプタでも
  無改変でビルドでき、3 経路すべて checksum 一致。**アダプタ境界の設計が正しかった**
- **ソースが無くても仕様は確定できる**: プリビルト `.a` の逆アセンブルで、ヘッダと食い違う
  実挙動 (上限 672、RX が BT スタックスレッド) を根拠付きで確定できた
- **組み込みの敵は計算ではなく電源とペアリング**: 6 個の地雷のうち計算に起因するものはゼロ
- **ホストで TDD できる形に切っておくと実機デバッグが激減する**: 実機で 1 回試す前に
  ホストで 1,788 checks。実機で出たバグ (SPP の重複送信) も**ホストのテストに落としてから**直した

**できていないこと (正直に)**

- **ノード内 2 コア並列は未達**: OpenMP は Stage-1 の逐次スタブのまま。2 個目のコア (CP) は
  音声処理が使っており、計算に取るには取り合いになる
- **slave 側のログが電波に乗らない**: IBRT の snoop リンクでは slave の SPP 送信が
  スタック上は成功扱いなのに実際には飛ばない。rank 0 が master の時しか PC に届かない
- **音楽を鳴らしながらの同時実行は未検証**: 「イヤホンとして使いながら裏で計算」はまだ道半ば
- **N を大きくした時のスケーリング**は未計測 (RAM 330 KB が上限、N=128 程度まで)
